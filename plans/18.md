## Goal
Add an optional `transaction_id` filter to `GET /alerts` so analysts can narrow alerts to a specific screened transaction without changing the existing filter behavior or alert scoring rules.

## Files to change
- `app/routers/alerts.py`
- `tests/test_alerts.py`

## Steps
1. Inspect the current `list_alerts` route and confirm how the existing query filters are applied and sorted.
2. Extend the `GET /alerts` signature in `app/routers/alerts.py` with an optional `transaction_id` query parameter that keeps the same `None` semantics as the other filters.
3. Apply the `transaction_id` filter after the status/assignee/risk-score filtering so the final result set remains consistent with the current alert order.
4. Add focused pytest coverage in `tests/test_alerts.py` for the new filter, including its interaction with the existing filters and the empty-result case.
5. Run the repo’s full test command from AGENTS.md to confirm no regressions in alert listing behavior.

## Tests to add
- `test_list_alerts_filters_by_transaction_id` — proves a single `transaction_id` query returns only the matching alert.
- `test_list_alerts_combines_transaction_id_with_existing_filters` — proves `transaction_id` works alongside `alert_status`, `assignee`, and `min_risk_score` without altering the current semantics.
- `test_list_alerts_returns_empty_list_for_unknown_transaction_id` — proves an unknown transaction ID produces an empty result set rather than an error.

## Success criteria
- `GET /alerts?transaction_id=<id>` returns only alerts for that transaction.
- Existing `GET /alerts` filters still behave the same when `transaction_id` is omitted.
- `GET /alerts` with a non-matching or unknown `transaction_id` returns `[]`.
- CI passes with `uv run pytest -v`.

## Risks
- Filtering by `transaction_id` could inadvertently change the default alert ordering if applied before sorting.
- Combining `transaction_id` with other filters could accidentally override or skip any existing filter.
- If the route uses a broad match instead of an exact transaction identifier, analysts could see unexpected alerts from related records.

## Rollback / escalation
- Revert the implementation PR to restore the prior alert-list behavior.
- No data migration or watchlist cleanup is required because this is a read-only filter addition.
- Escalate to a human reviewer if the change affects alert ordering, risk-score logic, or any screening decision path; this issue should stay limited to list filtering and must not modify screening rules or thresholds.

## Evidence to attach
- CI run link for the repository’s `test` job using `uv run pytest -v`
- Screenshot or log snippet showing `GET /alerts?transaction_id=<id>` returning only the expected alert IDs
- Test output from the new alert filter cases demonstrating unchanged behavior for the other alert filters

## Out of scope
- `infra/`
- `app/screening.py`
- Any change to `REVIEW_THRESHOLD`, `NAME_MATCH_THRESHOLD`, `LARGE_AMOUNT`, or other scoring decisions
- Changes to alert assignment, notes, close flow, or screening result generation unrelated to alert filtering
